Repeating Core Concepts –Layers
7Layers Pattern
•Problem : Complex systems tend to become entangled when all parts interact freely. This makes 
maintenance, reuse, and substitution of functionality difficult.
•Key building blocks
oLayers (e.g., Presentation, Business Logic, Data Access)
oInterfaces between layers
•Solution: Each layer provides services to the layer above it and uses services from the layer below it. This 
enforces clear dependency direction, hides internal details, and allows independent evolution of layers.
concept

Repeating Core Concepts –Model -View -Controller
8Model -View -Controller (MVC) Pattern
•Problem : User interface code often becomes tightly coupled with business logic, making systems hard to 
adapt to different UIs or devices.
•Key building blocks
oModel: domain data and business logic
oView: visual representation of the Model’s data
oController: mediator handling user input and 
coordinating updates
•Solution: The Controller interprets user actions 
and updates the Model. The Model notifies Views of changes (often via the Observer pattern). The 
Views refresh automatically. This separation allows 
independent modification of UI and logic.
concept

Repeating Core Concepts –Pipes and Filters
9Pipes and Filters Pattern
•Problem : Applications that perform complex data transformations often mix transformation logic and control 
flow, reducing flexibility and reuse.
•Key building blocks
oFilters: independent processing units transforming input to output
oPipes: connectors that pass data streams between filters
•Solution: Each filter processes data received from an upstream pipe and passes its output downstream. 
Filters can be rearranged or replaced to form new processing pipelines without changing the overall control structure.
concept

Repeating Core Concepts –Shared Repository
10Shared Repository Pattern
•Problem : Subsystems that need to share and maintain large amounts of common data often build their own 
ad-hoc data exchange logic, leading to redundancy and inconsistency.
•Key building blocks
oRepository (central data store)
oSubsystems or components accessing the repository 
via a defined schema or interface
•Solution: All components read and write to a 
common repository through standardized access interfaces. Consistency is ensured centrally, and each component can focus on its own processing logic rather than data exchange.
concept

Repeating Core Concepts –Microkernel
11Microkernel Pattern
•Problem : Systems with a stable core but many variable extensions (e.g., operating systems or domain 
frameworks) need a way to evolve without modifying the core.
•Key building blocks
oMicrokernel (core services): minimal runtime, communication, and management
oInternal servers: core subsystems directly managed by the kernel
oExternal plug -ins/adapters: application- specific extensions
•Solution: The microkernel provides basic mechanisms (e.g., service registration, communication). Plug -ins 
extend functionality through well -defined extension points. This enables portability, scalability, and flexibility 
while keeping the kernel stable.
concept

Repeating Core Concepts –Reflection
12Reflection Pattern
•Problem : Highly dynamic systems must adapt behavior or structure at runtime without recompilation, but 
typical static designs hard-code such logic.
•Key building blocks
oMeta -level + its components: maintains representations of system structure and behavior (metadata)
oBase -level + its components: performs normal application logic using meta- level definitions
•Solution: The base -level consults or modifies its meta -level descriptions at runtime to adapt behavior 
dynamically (e.g., changing object bindings or rules). This allows self -inspection, self -adaptation, and 
runtime reconfiguration.
