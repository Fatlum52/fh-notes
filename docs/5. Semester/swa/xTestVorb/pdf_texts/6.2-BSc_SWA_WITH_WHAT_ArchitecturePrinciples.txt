Motivation
Software architecture pays special attention to modifying and extending 
existing software in order to adapt it to changing needs (i.e., maintenance) or to 
use it for similar tasks (i.e., reuse ). 
Software systems can be divided into encapsulated components which are 
equipped with interfaces as their explicit abstractions. 
These components can then be replaced individually, combined in different 
ways, or supplemented .
In principle, caution is required: extension options that are never needed from the 
point of view of the business domain are simply superfluous, but cause costs. 
Design for reusability only makes sense if there are potential causes for 
reuse and not organizational, economic or other constraints stand in the way.

Overview
Originally, the object -oriented paradigm has developed from two needs :
Programming model based on modelling the real world (low representational gap).
Objects as cells, from which as by mutation variations can develop (adapt and reuse)
Programming model …
The paradigm offers a programming model that allows the world to be seen as a set of interacting 
autonomous objects . These objects encapsulate certain information and respond to (external) events 
on the basis of this information. 
The object -oriented model –with its data encapsulated in objects and operations that can be activated 
from the outside –offers the basic building blocks: individual objects with internal states and 
activatable behavior.
Objects as a basis for evolutionary fit software systems …
At the same time, the increasing size of software systems and respective investments resulted in the 
need to easily adapt existing programs to new or changing requirements. 
Software became expensive enough that people wanted to keep it in operation for as long as possible . 
By reusing existing software parts, one wanted to reduce the costs of expensive new software being developed.

Existing classes are reused in systems with extended functionality (e.g., JFrame in a window

Overview
The remaining chapters of this deck will focus on a subset of all Architecture 
Principles known as the SOLID principles …
Single Responsibility Principle . A class should have only a single responsibility (i.e., only one 
potential change in the software system specification should be able to affect the specification of the 
class).
Open / Closed Principle . Software entities should be open for extension, but closed for modification.
Liskov Substitution Principle . Objects in a program should be replaceable with instances of their 
subtypes without altering the correctness of that program.
Interface Segregation Principle. Many client -specific interfaces are better than one general -purpose 
interface.
Dependency Inversion Principle . Depend upon abstractions and do not depend upon concretions. 
Dependency injection is one method of following this principle.

©Ingo ArnoldSingle Responsibility Principle
Overview
An early step in object -oriented design is to figure out what objects should exist . 
In order not to get lost too early in the details and implementation-related aspects 
such as the exact attributes or signatures of operations, it helps to start with a relatively 
abstract assignment of responsibilities in the system. 
The overall system is divided into individual responsibilities , each of which is 
assumed by a dedicated object or class.
22
--- Page 23 ---
@ Ingo Arnold
©Ingo ArnoldSingle Responsibility Principle
The Principle
The principle demands that each class has exactly one responsibility, i.e. only 
one type of change in the system specification should be able to affect the class.
One reasoning behind this is that the code (i.e., the class) of an object that is 
responsible for several tasks at the same time must be changed every time one of 
these tasks changes.
There is a risk that a change in one area of responsibility will inadvertently 
affect another area covered by the same object. 
However, if the principle is adopted and the responsibilities are divided 
between two objects, the separation is clearer. If only the code of one of the classes is regenerated (compiled) at all, it is clear that the behavior of the other class is unaffected. 
By access modifiers (i.e., private) one can ensure, that methods, which serve a 
specific task are not misused for other tasks. Therefore, a change to such a private 
method can only affect one task.

Responsibility- driven Design (RDD)
A constructive design method can be derived from the single responsibility 
principle : Starting a list of responsibilities to be assumed by the system, a suitable 
object is introduced for each of them.
The design is thus driven by the fact that one is looking for responsibility holders. 
Hence the designation responsibility -driven design abbreviated with RDD . 
RDD helps to structure beyond the low representational gap (LRG), and if 
necessary leads to artificial objects, that take on specific responsibilities.

Class Responsibility Collaborator (CRC) Cards
The Class Responsibility Collaborator (CRC) model [Bellin Suchman 1997] is a 
collection of standard index cards that have been divided into three sections. 
A class represents a collection of similar objects, a responsibility is 
something that a class knows or does , and a collaborator is another class that a 
class interacts with to fulfill its responsibilities.

The problem with applying the single responsibility principle is that each developer has his own idea 
of the purpose of a component under consideration. 
Since we do not have clear instructions on how to implement this principle, different developers are 
left with their different interpretations regarding the responsibility of a component.
This means that in the end it is always the designer of an application who decides whether something falls within the scope of a component or not.
When designing a component with the SRP principle in mind, architects work with their subjective 
model of the problem domain as well as the business requirements .

©Ingo ArnoldOpen / Closed Principle
The Principle
The open / closed principle means open for extension and closed for 
modification.
More specifically this means that classes should be open to changes in their 
behavior and at the same time closed to changes in the code .
This principle formulates the desire that object behavior may change without 
recompiling their classes.
Often the open / closed principle leads to case distinctions being replaced by 
different subtypes, which bundle respective subtype behavior.

©Ingo ArnoldOpen / Closed Principle
Design Approach
In the object oriented paradigm, there are basically two mechanisms for changing 
the behavior of operations :
Overwriting methods viainheritance (e.g., method overwriting, template method pattern) or call 
redirection via object composition (e.g., decorator pattern)
Outsourcing the behavior into dedicated objects (e.g., strategy, state, or factory pattern).
An atomic method can only be replaced as a whole.
Alternatively, the algorithmic structure of a method could be represented as a 
combination of different individual methods, each containing single steps. Here, 
selected steps can be changed without having to entirely reprogram the overarching method. 
However, the method that controls the sequence could also be replaced and the 
existing individual steps recombined.

The Principle
62As a practical heuristic, the Liskov Substitution Principle states the following:
Subclasses and derived methods should expect no more and provide no less than their 
corresponding superclass . That is, a statement or property of the superclass should not be violated 
by the subclass.
A subclass should be able to take the place of the superclass . That is, functions with references to 
base classes must be able to use derived objects without being aware of it.

©Ingo ArnoldInterface Segregation Principle
The Principle
The interface segregation principle (ISP) requires that common supertypes of 
objects be defined based on the roles these objects can assume in the system.
In other words ISP requires that implementing classes are not forced to implement 
interfaces that they do not really need. 
When following the principle, split interfaces that are very large into smaller and 
more specific interfaces (i.e., role interfaces) so that their clients need to know only 
the methods that are of interest to them.
Each role interface declares one or more methods for a particular behavior 
(i.e., role). So instead of implementing one or a few fat interface(s), clients can 
selectively implement a needed role interface –an interface whose methods are 
relevant to them.
70
--- Page 71 ---
@ Ingo Arnold
©Ingo ArnoldInterface Segregation Principle
The Principle
Do not make yourself dependent on aspects you do not need. Interfaces that 
contain methods that are not specific to them are called dirty or fat interfaces and 
should be avoided.
Many custom interfaces are better than one general -purpose interface. When 
we have non-coherent interfaces, the principle guides us to create several smaller, 
coherent interfaces.

©Ingo ArnoldDependency Inversion Principle
The Principle
In a nutshell the dependency inversion principle (DIP) says that you should 
define variables and parameters of the weakest possible type (i.e., such that one 
does not need type casts for the use of the variables and parameters). 
The DIP relates to the interface segregation principle: A variable should be 
typed with exactly the roles that an object assigned to it really needs.
Based on this idea, Robert C. Martin’s [Martin et al 2003] definition of the DIP
consists of two parts:
High-level modules should not depend on low -level modules. Both should depend on abstractions.
Abstractions should not depend on details. Details should depend on abstractions.

©Ingo Arnold
Dependency Inversion Principle
The Principle
The programmed code is not dependent on the concrete object classes (i.e., 
actually referred objects), but only on role -defining interfaces (i.e., reference 
variable). 
The same independence applies vice versa for the classes or objects implementing 
these interfaces (i.e., extended class, extended interface).

This basic consideration also applies to the instantiation of objects , where the 
concrete classes to be used must be specified. This is the moment where (at the latest) 
dependencies arise again. 
An object should not generate needed objects, but receive them "from the 
outside". As long as this is respected, existing objects can work together with new or modified objects without any changes.
Technical tools for this are design patterns such as factory method, abstract 
factory or dependency injection (e.g., declarative approaches based on XML).

©Ingo ArnoldDependency Inversion Principle
Dependency Injection
Dependency injection (DI) is the concept in which objects get other required 
objects from the outside .
A class has a dependency on another class, if it uses an instance of this other 
class (i.e., class dependency). For example, a class which accesses a logger service 
has a dependency on this service class.
Ideally classes should be as independent as possible from other classes. This 
increases the possibility of reusing these classes and to be able to test them 
independently from other classes.
If a class creates an instance of another class via the new operator, it cannot 
be used (and tested) independently from this other class . This is called a hard 
dependency.

Design Approach
In order to comply with the DIP, you have to create the necessary abstractions 
in the type hierarchy first – this means the abstractions you want to use when typing 
variables and parameters. 
Role models you have developed in the context of the interface segregation 
principle (i.e., program to interfaces) may be helpful.
Abstract types should be formulated as interfaces (i.e., not as abstract classes). 
The primary purpose of abstract classes is to provide code for other classes 
via inheritance (i.e., sub -classing). However, this is a task independent of subtyping, 
which should therefore be separated.
Finally you need to pay attention to introducing variables and parameters as 
abstract types wherever possible.

•Architectural principles are experience -based rules that promote maintainable , evolvable , and 
understandable systems.
•They are interrelated –for example, loose coupling supports high cohesion and modularity .
•Key Relationships
•Modularity . Enables black -box design and separation of concerns.
•Abstraction. Defines clear boundaries between interface and implementation.
•Information Hiding. Encapsulates internal details, improving change tolerance.
•Loose Coupling ↔ High Cohesion. Minimal dependencies, strong internal unity.
•Incrementality . Systems evolve stepwise with minimal rework.
•Design for Change. Anticipate and localize future modifications.

■SOLID Principles
•Single Responsibility Principle (SRP)
•Each class should have exactly one reason to change –one area of responsibility .
•Reduces side effects and clarifies system structure.
•Supports Responsibility -Driven Design (RDD) (method could be: Class -Responsibility -Collaborator (CRC) cards).
•Typical responsibilities: creator , controller , information expert .
•Risk isover -fragmentation; balance cohesion and simplicity .Wrap -Up

•Open / Closed Principle (OCP)
•Software entities should be open for extension but closed for modification.
•Behaviour can change without altering existing code.
•Techniques
•Inheritance (e.g., template method pattern).
•Composition and delegation (e.g., strategy, state, decorator patterns).
•Encourages polymorphism and plug-in architectures.
•Avoids case distinctions and repeated modifications of base classes.
•Liskov Substitution Principle (LSP)
•Subtypes must bereplaceable for their supertypes without changing program correctness.
•A subclass must not violate contracts or expectations defined by its base type.
•Violations occur when methods cannot bemeaningfully implemented (e.g., Bicycle.startEngine()).
•Fix: design correct hierarchies and use interfaces to separate incompatible concerns.Wrap -Up

©Ingo Arnold 100■SOLID Principles –continued
•Interface Segregation Principle (ISP)
•Clients should not depend on methods they do not use.
•Prefer many small, role-specific interfaces over few large general-purpose interfaces.
•Promotes modularity , reusability , and testability .
•Each interface defines a specific role; classes may implement multiple roles as needed.
•Dependency Inversion Principle (DIP)
•High-level modules should not depend on low-level modules –both should depend on abstractions.
•Abstractions should not depend on details; details should depend on abstractions.
•Achieved by
•Interfaces and abstractions between layers.
•Dependency Injection (DI) and Factory Patterns to supply dependencies externally .
•Improves testability , flexibility , and isolation of changes.Wrap -Up
